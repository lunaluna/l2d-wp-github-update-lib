# 既知の課題: l2d-updater が GitHub API の失敗原因(特にレート制限)を区別しない

- 記録日: 2026-10-03
- 対象バージョン: 1.2.0(`dist/class-l2d-github-updater.php`)
- 状態: **記録のみ。未対応。** 対応するかどうかは未決定(下の「対応する場合の論点」を参照)
- 発見の経緯: WP Checksum Verifier(WPCV)の v0.9 プラン作成中に、同梱されている `lib/l2d-updater` を読んで指摘された。WPCV の範囲外のため、共有ライブラリ(このリポジトリ)側の課題として記録する
- 根拠: このリポジトリの実ソースを読んで確認済み。行番号は 1.2.0 時点のもの

## 1. 現状の挙動(確認済み)

### 1-1. 失敗の扱いは原因を問わず一律

`request_latest_release()`(`dist/class-l2d-github-updater.php` L416-467)は、次のどれでも `null` を返す。

| 条件 | 該当箇所 |
|---|---|
| 通信エラー(`WP_Error`) | L438 |
| HTTP ステータスが 200 以外(403・404・429・5xx など全部) | L442 |
| レスポンス JSON に `tag_name` が無い | L452 |
| 条件に合う zip アセットが無い(`asset_pattern` 不一致、`draft` のみなど) | L457 |

`fetch_latest_release()`(L383-408)は `null` を受け取ると、空配列 `array()` を site transient(キー: `cache_key`)に保存する。保持期間は `backoff_ttl`(既定 1800 秒 = 30 分、L146)。

`array() === $cached` の間は「バックオフ中」とみなし、GitHub を呼ばずに `null` を返す(L390-392)。

### 1-2. 読んでいないもの

次の処理はこのライブラリのどこにも無い(grep でヒットなし)。

- HTTP ステータス 403 / 429 の判定
- `x-ratelimit-remaining` / `x-ratelimit-reset` / `retry-after` ヘッダーの読み取り
- 失敗の理由(HTTP コード・エラー種別)の保存

### 1-3. 設定できる範囲

- `backoff_ttl` は設定キーと、フィルタ `l2dwpghul_updater_backoff_ttl`(`filter_prefix` があれば旧名 `{prefix}_github_updater_backoff_ttl` も)で変えられる(L636-643)
- ただし変えられるのは**固定の秒数だけ**。失敗の種類によって変わる仕組みは無い
- `enabled` フィルタで更新確認ごと止めることはできる

### 1-4. 既存テスト(`tests/GitHubUpdaterTest.php`)

- 403 のレスポンスで `null` が返ること(約 L404)
- バックオフ中は再取得しないこと(約 L355)
- 失敗の種類ごとに TTL が変わる、という挙動のテストは**無い**(挙動自体が無いため)

### 1-5. README の記述

`README.md` L75 に「GitHub API の未認証レート制限(実測 60 req/h)に配慮した設計」とある。実際の配慮は「30 分の固定バックオフ」だけで、リセット時刻は見ていない。

## 2. 失敗の原因ごとの影響

| 失敗の原因 | 今の挙動 | 起きうる問題 |
|---|---|---|
| レート制限(未認証 60 回/時を使い切った) | 30 分固定で待つ | リセットが 30 分より後なら、再試行がまた失敗し、さらに 30 分待つ。その再試行は API 回数を無駄に使う。逆に数分で解ける場合も 30 分待つので、更新の検知が遅れる |
| 一時的なネットワーク障害・5xx | 30 分固定で待つ | 短い待ちで足りる場合でも 30 分遅れる |
| 恒久的な失敗(リポジトリ名の誤り、アセット名の不一致、`asset_pattern` の不一致) | 30 分ごとに再試行し続ける | 直らないのに呼び続ける。原因が残らないので、運用者が「更新が来ない」理由を切り分けにくい |
| 成功したがリリースが無い(404 = Release 未作成) | 30 分ごとに再試行 | 上と同じ |

補足:

- 失敗の理由を保存しないので、「更新が来ない」ときの調査は、実際に GitHub を叩き直して見るしかない
- トークン(`token` 設定)があれば認証済みの上限(未認証より大きい)が使われるが、トークンを使う構成は限られる(利用側プラグインの実際の設定は**未確認**)

## 3. 影響の大きさ(未測定)

**以下は推測であり、実測していない。**

- WordPress の更新確認は通常 12 時間ごとに走る見込みで、成功時のキャッシュは 6 時間(`cache_ttl` 既定 21600 秒、L145)。この組み合わせなら、通常は 1 サイトあたり 1 日に数回の呼び出しで、60 回/時には当たらない見込み
- ただし、共有ホスティングで**同じ IP から多数のサイトが未認証で GitHub を呼ぶ**場合は、IP 単位の上限に当たる可能性がある(未確認)
- 実際に困ったという報告は、今のところ無い。30 分の固定バックオフでも、壊れてはいない
- 実際の呼び出し頻度(`update_plugins` を更新する契機の数、管理画面を開いたときの強制確認など)は測っていない

## 4. 参考: WPCV 側の実装(このリポジトリからは未確認)

WPCV の `WPCV_GitHub_Client` は、これを区別している(WPCV v0.8 の D9)と指摘された。内容は次のとおり。

- 403 / 429 で `x-ratelimit-remaining: 0` が返る、または `retry-after` がある場合を `rate_limited` として扱う
- リセット時刻まで、同じ run の残りの GitHub 照合を止める

このリポジトリの作業としては、WPCV のコードを**読んでいない**。対応する場合は、実装を移植する前に、WPCV の実ソースで挙動を確認すること。

WPCV の GitHub 照合と l2d-updater の更新確認は、別の経路。l2d-updater が使うのは自分自身の Release 1 件だけで、WPCV の機能には影響しない。

## 5. 対応する場合の論点(未決定)

実装を決めるものではなく、プラン作成のときに潰すべき点の一覧。

1. **ヘッダーの仕様を一次情報で確認する**: `x-ratelimit-remaining` / `x-ratelimit-reset`(エポック秒か)/ `retry-after`(秒数か)/ 403 と 429 のどちらで返るか、を GitHub の公式ドキュメントと実レスポンスで確認する。記憶で断定しない
2. **失敗の分類**: 少なくとも「レート制限」「一時的(通信エラー・5xx)」「恒久的(404・アセット不一致)」を分けるか。分類ごとの待ち時間を決める前に、実測する(CLAUDE.md の「数値を決める前に実測する」)
3. **状態の組み合わせ表**: キャッシュ有無 × 失敗の種類 × 残り時間の表を作り、各セルの挙動を決める(特に、リセット時刻が遠すぎる値のとき上限を設けるか、`retry-after` が不正値のときの扱い)
4. **失敗理由の保存**: transient に何を持たせるか。現在は `array()` が「バックオフ中」の印になっており(L390)、形を変えると、旧版が書いた `array()` との互換(複数プラグインが異なる版を同梱する構成)に影響する
5. **利用者から見える挙動の変更**: 反映速度・待ち時間が変わるため、変更理由と副作用を申告して承認を得る(CLAUDE.md の「既存の挙動に影響する値の変更は申告する」)
6. **リリースと展開**: このライブラリのリリース手順(CLAUDE.md の「リリース手順」)に従い、その後、利用側(WPMAR・FAUC・FCSE・WPCV など)で `plugin-release.yml` の参照タグと `git subtree pull` の更新が別途必要
7. **テスト**: 403/429 のヘッダー付きレスポンス、`retry-after` のみ、ヘッダー無しの 403、5xx、404 の各ケース

## 6. 着手するときの進め方

- プラン作成と実装は別セッション(全プロジェクト共通のルール)
- プランの前に、上の論点 1(ヘッダー仕様の確認)と、3 節の未測定事項(呼び出し頻度)の測定を行う
- 本書は「記録」であり、プランではない
